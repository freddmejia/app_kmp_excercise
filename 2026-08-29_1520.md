## 3. ⚠️ Two documented decisions, reversed on purpose

Both files argued their case at length. Both arguments were right in the abstract and
wrong in use, and the new comments say so rather than quietly overwriting them.

### `ActivityCategory.sq`: *"Deliberately NOT a second measurement_type"*

The old reasoning: a measurement type is a **closed contract** — it decides which
logging form applies and which metrics exist, so it cannot be user-extended without
code. A category is **free-form organisation** — it constrains nothing and feeds no
metric. Orthogonal, therefore separate.

What that produced: "Running" the category and `DISTANCE_TIME` the type are one fact,
asked as two questions, and nothing stopped you answering them inconsistently — an
activity filed under Bicycle that opened the muscle form.

The type is still closed and still decided in code. What changed is that the user
reaches it by picking a category rather than from a second list beside it. A category
stopped being organisation and became a contract, which is a real loss of freedom and
the reason the reversal is written down rather than assumed.

### The Activities tab

Its own log entry (2026-08-21 §"Activities screen splits rather than filters") defended
the trained/untrained split, and the 2026-08-29 09:40 session put a week strip on it.
That was the tell: the tab had grown a week strip and a per-day split, so **two tabs
answered "what did I do this week?" in two different shapes**.

It also cost something concrete. On a day you trained nothing, the whole catalogue was
hidden behind an empty state — so editing an activity meant first hunting for a day you
had used it. A screen whose entire job is editing cannot put its rows behind a date.

The catalogue survives, in Preferences beside Muscles and Categories, as a flat list
with no strip and no New button. **An activity is created by logging one now.**

## 4. `activity.measurement_type` stays, and why that is not two sources of truth

The category decides the type; the activity records it. Both columns exist.

- **A category is optional.** `category_id` is nullable and `ON DELETE SET NULL`
  produces nulls on its own, so "read it through the category" has no answer for a
  perfectly normal row.
- **History was recorded under the activity's type.** Letting a category edit rewrite
  it would leave a strength activity pointing at distance columns it has no values for
  — the numbers would stay and their meaning would move.

So `UpdateCategoryUseCase` changing the type decides what is filed there *next* and
never reaches what is already there. That is in its KDoc, because "changes nothing
that exists" is not what anyone assumes a type field does.

The old rule survives intact: **a type with sessions behind it cannot move.** It is
now reached by refiling an activity into a category that measures something else, and
`ChangeMeasurementTypeUseCase` refuses it exactly as before.

## 5. The migration: inherit, and split what cannot inherit

`5.sqm`, schema 5 → 6. Every existing category takes the measurement of the activities
inside it — the most common, archived ones included, ties broken on the type name so
the result does not depend on row order. An empty category keeps the column default.

A category holding **both** kinds cannot inherit one without lying about the other, so
the minority moves to a copy carrying the original's icon, colour and `created_at`.
The copy is named `<name> · STRENGTH`, and the raw enum is deliberate: **a migration
cannot resolve a string resource** — there is no locale in a `.sqm` — and hard-coding
an English phrase would be worse than an obviously mechanical suffix. It is a rename
prompt, and it only appears for a category that genuinely held both.

`INSERT OR IGNORE` guards the one collision that would otherwise abort the upgrade and
kill the app on launch: a category already named exactly `X · STRENGTH`. When it fires,
the reassignment finds no compatible target and those activities come out
uncategorised — a state the app already handles — instead of pointing at a category
that measures something else.

Four new migration tests cover it, including the split, and one asserts the thing the
split must never do: **no activity's own measurement type is rewritten.** The split is
about where things are filed, never about what they are.

## 6. Gym, Swim, Bicycle — the same seed machinery as the muscles

Asked for directly: *"for categories I think always have a GYM, Swim, Bicycle"*.

Yesterday's `seed_key` + ledger design (see [`2026-08-29_1210.md`](./2026-08-29_1210.md)
§3) was copied wholesale — a key on shipped rows, null on the user's, null again once
they rename one, and a `category_seed` table so a deletion sticks. Names follow the
device language; the **measurement type does not** and is written once at insert,
because a shipped category that changed how it measures would reinterpret every session
under it.

A separate ledger table from `muscle_seed` rather than one generic table with a `kind`
column: `4.sqm` had already shipped to the emulator, and rewriting a released migration
to save one table is the wrong trade.

**Why exactly three.** They are one of each *shape the app can log* — Gym opens
muscles-and-sets, Swim and Bicycle open distance-and-time. Every logging path is
reachable on a fresh install without creating anything. Swim and Bicycle sharing a type
is not redundancy: they are different training with separate history, and two of them
being present is what shows a user that the same form serves more than one thing.

## 7. ⚠️ The bug the emulator caught that no test would have

Picking **Bicycle** opened **Gym's** screen — "Logged as: Strength", Gym's activities
listed, and the name typed on the previous visit still in the field.

`koinViewModel { parametersOf(categoryId, epochDay) }` with no `key`. The ViewModel
store is the Activity's, so it hands back the instance built for the *first* category
ever opened, with that category baked into its constructor, for every category after.

`WorkoutEntryScreen` already documents this exact hazard, three lines from where I
would have read it:

> *Keyed by what the screen is about. Without this the store hands back the ViewModel
> built for the first log ever opened, with its activity and day baked into the
> constructor, for every log after it.*

Every parametrised screen in this app passes a `key`. Mine did not. Two fixes, because
there are two halves and the key only covers one:

- `key = "new-log-$categoryId-$epochDay"` — a different category is a different screen.
- `onOpened()` on every appearance — the *same* category opened twice legitimately
  reuses one instance, and it would still open on the name typed and abandoned last
  time. That is the convention every editor here follows.

**No host test would have caught this.** The tests construct the ViewModel directly
with its parameters; the bug lives entirely in how Compose resolves it. This is the
argument for the "verify on a device" rule the previous logs keep making, stated as an
actual failure rather than as a principle.

The near miss underneath it: I found this only because a *different* mistake — tapping
without dumping first, against the 2026-08-29 09:40 log's own "dump, then tap, every
time" rule — sent a tap into the wrong row and made me redo the walk properly.

## 8. The other bug, in the save path

`ActivityEditorUiState.type` derives from the selected category by looking it up in
`categories`. But `categories` is merged in by the **state combine**, and `save()`
reads `form.value` — which never has it. So every activity saved through the editor got
`STRENGTH` regardless of its category. Three tests failed at once and said so.

`resolveType()` now asks the repository at save time. That is not just a fix, it is the
more correct source: `state.value` is a `WhileSubscribed` combine, so its category list
is whatever the last collector saw — empty with nothing collecting, and stale if the
category was edited on another screen since.

- **Pre-existing activities are uncategorised, so they appear in no reuse list.**

  form; that form no longer asks. A category *can* still be created as SIMPLE from the
  category editor, and nothing can be logged against it — the same gap the 2026-08-21
  log recorded, one level further from the surface. Either give it a form (a name and a
  day, nothing else) or drop the enum value.
- **Three strings orphaned before this session** are still there:
  `log_no_strength_activities`, `log_distance_time_title`, `plural_days`.
- **`CategoryMessage.Saved/NameBlank/NameTaken` are now unreachable** — the ViewModel
  that emitted them lost the methods that did. The screen still renders them.

  showed the name and the measures on one page. Making the entry screen work with a
  late-bound activity means rebuilding `WorkoutEntryViewModel` around a `StateFlow`

  in the back stack instead, which costs one extra screen and no rework. Worth revisiting
  if the two-step flow starts feeling long.
