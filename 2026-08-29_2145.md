## 3. ⚠️ System back pops the stack — the oldest open item, closed

Asked for as *"add swipe to comeback when you enter in another screen like a detail"*.

Every log since 2026-08-21 carried this: **"Android's system back still exits the app
rather than popping."** The cause was structural. `App.kt` keeps its own back stack —
there is no navigation library — and Android's back went to the activity, which knew
nothing about it. So the gesture people reach for first threw away what they were doing,
and every screen had exactly one way out: the arrow in the app bar.

```kotlin
BackHandler(enabled = backStack.size > 1) { pop() }
```

- **`enabled` matters.** At a tab root, back must still leave the app. Intercepting it
  there would make the app impossible to exit by ordinary means.
- **It calls the same `pop()` as the arrow.** Two ways out running different code would
  drift, and the arrow is the one with coverage.
- **`ui-backhandler` is a separate artifact.** Not transitive from `compose-ui`;
  `implementation(libs.compose.ui.backhandler)` in `commonMain`.
- **It is experimental in CMP 1.11**, and the opt-in says why: the multiplatform
  contract around a "back" that iOS expresses as an edge swipe and Android as a gesture
  or a button is still settling. On Android it compiles to `OnBackPressedDispatcher`,
  which is not experimental.
- **No manifest change.** `targetSdk` is 36, where predictive back is already the
  default, so the gesture gets its animation without `enableOnBackInvokedCallback`.

Verified three ways on the emulator: the back *button* pops, a real left-edge swipe
pops, and back at a tab root still returns to the launcher.

**This is a common-code fix, so iOS gets it too** — and iOS has no system back at all,
which made the app-bar arrow the only exit there. That half is still unverified, like
everything else on that platform.

## 7. Both bars lost their bands

Three requests, arriving one after another, each following from the last.

### The bottom bar

*"delete background color for menu tab"* — which had two readings, the grey band under
all three tabs and the blue pill behind the selected icon. Asked; **the band**.

M3 defaults `NavigationBar`'s container to `surfaceContainer`, which put the bar a step
above the screen and drew a grey strip across the bottom. It is `Color.Transparent`
now, so the bar takes whatever is behind it.

- **`tonalElevation = 0.dp` as well, and it is not redundant.** M3 paints a surface
  tint on top of the container colour, so leaving the default 3.dp would have drawn the
  band back on in a slightly different shade.
- **Transparent rather than naming `background`**, so the bar cannot disagree with the
  Scaffold it sits in — including over the system gesture strip, which this bar extends
  under and therefore paints.
- The tabs read fine without it: an icon, a label, and a filled pill on the selected one
  are already three signals, and the strip was spending a band of colour to say
  something none of them needed help saying.

### Then a rule, to give the edge back

*"add line separator for menu tab with color gray and 1 pixel of height."* Removing the
band had removed the boundary too, and a list scrolled to the bottom ran straight into
the tabs. A `HorizontalDivider` above the bar does the same job with one line instead of
a filled strip.

- **One physical pixel, not one dp**, because that is what was asked for and it is the
  right unit for this one thing: a separator should stay hairline-thin however dense the
  screen is, and at 420dpi a `1.dp` rule is nearly three pixels and reads as a border.
  `with(LocalDensity.current) { 1.toDp() }`. Everything else in this app is in dp
  precisely because it should scale, so the exception says so out loud.
- **`outlineVariant`, not a named grey.** It is grey in the light scheme and a
  different, correct grey in the dark one — which a hard-coded `Color.Gray` could not
  be, and this app has a full dark palette.
- The divider and the bar share a `Column` in the `bottomBar` slot, so the rule sits
  above the tabs and outside the window insets the bar pays for.

### And then the top bar, to match

*"do it the same for title tab top bar."* Transparent container, one hairline rule below
it. The two bars frame the screen and have to agree — that was the argument for painting
both `surfaceContainer` in the first place, and it is the same argument now that neither
is painted. A bar with a band above a bar without one reads as a mistake whichever way
round it is.

The only difference between them is which side the rule sits on: below the top bar,
above the bottom one — each rule between the chrome and the content it separates from.

One thing kept rather than defaulted: `titleContentColor` and
`navigationIconContentColor` are still named. With a transparent container M3 resolves
those against `surface`, and this app's screens are not all `surface` — leaving them to
the default is how a title ends up the right grey on two screens and the wrong one on
the third.
