## 3. Decisions worth remembering

These are the ones that took thought, and that a future change could easily undo by
accident.

### Categories vs measurement type
`MeasurementType` (STRENGTH / DISTANCE_TIME / SIMPLE) stays a **closed Kotlin enum**
— it decides which logging form applies and which metrics exist, so it cannot be
user-extended without code. A **category** is free-form user data, orthogonal to it.
"Running" is a category; the activity in it is measured as `DISTANCE_TIME`.

### Delete semantics differ per entity, on purpose
- **Activity / muscle** — hard delete refused once sessions reference them; archive
  instead. Deleting would break past metrics.
- **Category** — delete always allowed; its activities become uncategorised. Nothing
  references a category except a label, so there is no history to protect.
- **Body weight** — delete always allowed. Nothing references a measurement.

### `ON DELETE CASCADE` is not trusted anywhere
It only fires while `PRAGMA foreign_keys` is on, which is a **per-driver setting** —
true on Android and iOS, false in the JDBC driver the tests use. Every cascade is
also done **explicitly inside the same transaction**, so behaviour is identical
everywhere. Applies to: category delete, activity/muscle link cleanup, session delete.

### The week strip
- The **week is derived from the selected day**, so tapping a day inside the visible
  week cannot move the strip. Only the arrows and the date picker change weeks.
- Arrows step **±7 days**, not "to next Monday", so the weekday column stays put.
- `weekStartOf()` floors its modulo — Kotlin's `%` keeps the dividend's sign, which
  would throw pre-1970 dates into the following week. There is a test for this.
- Monday-first is **hardcoded**; some locales start on Sunday.
- **Browsing days never writes.** Creating a session/reading is always an explicit act.

### The activity → muscle link is a default, never a restriction
No links = "not specified", so the picker falls back to the whole catalogue (an empty
picker would make the activity unloggable). An unlinked muscle is still loggable, and
a muscle already checked is always shown even when the picker is scoped — otherwise
its sets count toward the totals with no visible row to correct.

### Activities screen splits rather than filters
The week view shows *Trained this week* and *Not trained this week* as two sections.
It must not hide rows: this is also the screen that creates, archives and deletes
activities, and an activity made seconds ago has trained nothing.

## 4. Bugs found and fixed

Including several introduced earlier in the same session.

1. **Body-weight readings dated in the future were invisible.** The day strip made
   future days selectable, but history/chart ranges still ended at `today` — so rows
   could be created that no screen would ever show or delete. Fixed both ends: ranges
   now end at `max(today, latest reading)`, and logging a future day is refused
   (`LogBodyWeightResult.FutureDay`).

2. **Overwrite confirmation was never wired.** `checkForOverwrite()` and
   `WillOverwrite` existed but nothing called them, so same-day logging replaced
   silently. Replaced with state the form renders *before* you press: the button says
   **Log** or **Replace**, with "Already N kg — saving replaces it."
   *(One reading per day is by design — `date_epoch_day` is UNIQUE and the write is
   `INSERT OR REPLACE`. The row `id` changes on each overwrite, which is why repeated
   logging looks like new rows being added.)*

3. **History list squeezed to zero height** on the Weight screen after the strip was
   added — a nested `LazyColumn` gets whatever constraints remain. All five screens
   now use `Modifier.weight(1f)` so the list claims the leftover space explicitly.

4. **A checked muscle disappeared when the picker was scoped**, while its sets kept
   counting in the totals. Fixed by `includingChecked()`.

5. **iOS caught what Android didn't:** `DatePicker` is stable in the Android
   material3 artifact but still experimental on Kotlin/Native, so `assembleDebug`
   passed while `compileKotlinIosSimulatorArm64` failed. *Always build both.*

6. **Dates and enum labels were silently English.** `dayOfWeek.name.take(3)` produced
   "Mon"/"Tue" only because the Kotlin enum is written in English; same for months and
   for `ActivityFilter.name.lowercase()`. All now index off the enum **ordinal** into
   string resources.

## 5. Internationalisation

- `shared/src/commonMain/composeResources/values{,-es,-it,-fr}/strings.xml`
- **164 keys × 4 locales**, plus 7 `<plurals>` sets. Parity of keys *and* `%n$`
  argument counts is checked — a mismatch throws at runtime in one language only.
- Apostrophes are escaped `\'`; a bare one truncates the rest of the string.
- Even the **order of date parts** is a resource (`date_full`), so a locale can put
  the month first without code changes.
- Follows the **device language**. There is no in-app language picker.
- Translations were written during this session and should be skimmed by a native
  speaker before shipping.
