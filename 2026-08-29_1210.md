## 2. What ships, and how coarse it is

Asked for as *"more significant muscles for gym, example, chest, chest middle-low
etc, because I don't need create group muscle etc, it should appear from the app"*.
Offered three granularities; **compact** was chosen — one leaf per muscle people
train *separately*, no head-by-head anatomy.

| group | leaves |
|---|---|
| Chest | General, Upper chest, Middle chest, Lower chest |
| Back | General, Lats, Traps, Rhomboids, Lower back |
| Shoulders | General, Front delt, Side delt, Rear delt |
| Arms | General, Biceps, Triceps, Forearms |
| Legs | General, Quads, Hamstrings, Glutes, Adductors, Calves |
| Core | General, Upper abs, Lower abs, Obliques |
| Neck | General |

- **Every group ships a "General" leaf**, which is what `MuscleCatalog.sq` has always
  said should happen. Sessions reference a leaf and never a group, so without it
  "I trained chest" has nowhere to go.
- **The three delt heads are the one head-by-head split kept**, because they are
  trained by different movements on different days. There is no vastus medialis: a
  leaf nobody logs is a row everybody scrolls past.
- **Gym vocabulary, not textbook vocabulary** — "Lower back", not "erector spinae".
- **Order is alphabetical**, so the app shows Arms, Back, Chest, Core, Legs, Neck,
  Shoulders rather than the order above. That was a decision, not an oversight: every
  catalogue query already sorts by name, a user-made group has no natural position
  among shipped ones, and alphabetical is the only ordering that interleaves the two
  coherently. A `sort_order` column would pile every user group at one end.

## 3. Localisation without touching a single query

The hard part. Muscle names are the only user-visible text in this app that lives in
the **database** rather than in a resource, and six queries read `muscle.name` /
`muscle_group.name` directly — the picker (twice), group volume, muscle volume,
untrained, session detail.

The obvious design is a resource key on the row and a lookup at render time. That
means carrying the key through all six queries, both mappers, four domain models and
every screen that shows a name. It was rejected.

**What was built instead: the names stay plain text, and a start-up pass rewrites
them.**

```
muscle.seed_key  →  set on a row the app shipped
                    null on a row the user made
                    null again the moment they rename it
```

Nothing above the repository changed. Every query is still a name lookup. The three
rules that make it work:

- **A key names a row; a resource names its text.** All seven "General" leaves share
  one string resource and each has its own key (`chest.general`, `back.general`, …).
  The key is written down in `ResourceMuscleSeed.kt` forever — change one and the next
  launch treats it as a new muscle and inserts a duplicate beside the old.
- **Renaming clears the key.** That is the whole ownership rule, and it is enforced in
  SQL rather than in Kotlin: `renameMuscle` is `UPDATE muscle SET name = ?, seed_key =
  NULL`, so no future caller can rename a row and forget to release it.
- **The `muscle_seed` ledger holds every key ever inserted**, whether or not its row
  still exists. Without it, deleting a shipped muscle would be undone on the next
  launch — the sync would see it missing and put it back. This is also why *adding* a
  group in a later version needs no migration: the ledger, not the schema version, is
  what says "already done".

`SyncMuscleSeedUseCase` runs on every start, because it answers two questions and
installing only settles the first: *is the catalogue there* and *is it in the right
language*. It writes nothing when there is nothing to change, so a same-language start
raises no query notification and no Flow in the app re-emits.

### The effect key in `App.kt` is a translated string

```kotlin
val languageKey = stringResource(Res.string.muscle_seed_general)
LaunchedEffect(languageKey) { sync() }
```

`Unit` is the obvious key and is right for the install case and wrong for the language
case: `getString` resolves against whatever language is current *when it runs*, so a
sync that never runs again can only have written the language the app first started
in. Both platforms do usually recompose from scratch after a language change, which
would make `Unit` enough by accident; keying on a seeded name makes it enough on
purpose — it changes exactly when the translations do.

## 4. "Add alongside", and why not merge by name

Also chosen by the user, and it is the right answer for a reason worth writing down:
the alternative was to merge a seeded group into an existing one with the same name.

The emulator database made the case by itself. It already held a hand-made group
`pecho` with leaves `alto` / `bajo` / `medio` — the same three muscles as the seeded
`Chest`, in a different language, under different names. Name matching would not have
merged those, and *would* have merged a group called "Chest" that the user meant as
something else. There is no undo for a merge. There is an undo for a duplicate: delete
one.

So the migration adds two nullable columns and touches no row. Everything already on a
device comes out of it reading as user-owned, which is what it is. Verified on the
real device database, not just in memory — §7.

## 5. ⚠️ `last_insert_rowid()` is per **connection**, not per table

The bug that took the session's one debugging detour. Fourteen tests failed at once
with `FOREIGN KEY constraint failed` on inserting the first leaf.

```kotlin
queries.insertSeededGroup(...)
queries.markSeedApplied(group.key, now)   // ← another INSERT
groupsAdded++
queries.lastInsertRowId().executeAsOne()  // ← the ledger's rowid, not the group's
```

The ledger write sits between the insert and the read, so every leaf was inserted
against a group id that belonged to a `muscle_seed` row. `last_insert_rowid()` is
connection-scoped and does not care which table you meant.

The fix is to read it on the very next line. The general rule, now in a comment there:
**between an insert and its `lastInsertRowId()`, nothing else may write** — and
`markSeedApplied` does not look like a write at a glance, which is exactly why it got
in there.

Every other `lastInsertRowId()` in this codebase was checked; the rest read it
immediately.

## 6. ⚠️ Deleting a muscle group has always been broken

Found while writing the tests, and it is not a bug this session introduced — it is one
this session would have made reachable for every user on their first attempt.

`muscle.group_id REFERENCES muscle_group(id)` has **no `ON DELETE` clause**, so SQLite
defaults to `RESTRICT`, and both production drivers set `PRAGMA foreign_keys=ON`.
`deleteGroup` checked history, deleted the activity links, then deleted the group row
— and never deleted the leaves. So deleting any group that had leaves failed outright
with a foreign key error.

Nobody had hit it because a group with leaves and *no session history* is a narrow
window when you build the catalogue by hand. With a shipped catalogue it is the
ordinary case: every one of the seven groups has leaves and none has history, so the
first user to try removing "Neck" would have hit it.

Fixed by deleting the leaves inside the same transaction, before the group.
`countSessionsForGroup` has already established that none of those leaves has history,
which is what makes it safe rather than lossy — and there is now a test asserting the
history block still fires, so "delete the leaves" did not quietly widen what a delete
is allowed to destroy.

**The host test sets `PRAGMA foreign_keys=ON` on the JDBC driver**, which the previous
suites did not. Without it this path passes on a host and fails on a device — the
whole class of bug the migration tests exist to catch, in a different disguise.

### Emulator notes, on top of the 2026-08-29 09:40 set

- **`adb` is not on `PATH`** in this shell. It is at
  `/c/Users/Usuario/AppData/Local/Android/Sdk/platform-tools`.
- **Reading the app database without `sqlite3`.** The emulator image has no `sqlite3`
  binary, so `run-as … sqlite3` fails. What works is pulling the file and reading it
  on the host: `adb exec-out 'run-as <pkg> cat databases/gym.db' > out.db`, then
  Python's `sqlite3`. It must be `exec-out`, not `shell` — `adb shell cat` mangles
  binaries, as the 2026-08-24 log already recorded for PNGs. The file arrived 92 bytes
  longer through `shell` and would not open.
- **Windows Python cannot open an MSYS path.** `/c/Users/...` has to be `C:/Users/...`
  before it reaches the interpreter, even though the shell resolves it fine.
