so nothing was lost by letting the label move.

## 3. Decisions worth remembering

### `safeContentPadding()` was silently adding ~24.dp of side margin

This is the one to remember. `App.kt` wrapped the whole `Scaffold` in
`safeContentPadding()`. That is safeDrawing **union safeGestures**, and safeGestures
carries the back-swipe exclusion strips down the left and right edges — roughly 24.dp
a side on a gesture-nav device.

It is applied outside every screen, so a screen asking for 10.dp side margins got
34.dp, and **no amount of editing that screen could change it**. Now
`safeDrawingPadding()`. Status bar, navigation bar and display cutout are still
honoured; only the gesture strips are dropped, and those intercept *swipes*, not taps —
nothing in this app is dragged horizontally.

Measured on the emulator (1080×2424 @ 420dpi): day cells went **~35.dp to 45.dp**, side
margins **~34.dp to ~10.dp**.

Note `safeDrawing` still includes **IME** insets, so the keyboard continues to push
content up. That is wanted.

### Bare `clickable` needs an explicit semantics label

The date text and the caret are `Modifier.clickable` on plain content, not buttons.
Without `onClickLabel` plus `Role.Button`, TalkBack announces the caret as the literal
character. The two retired string keys were reused for exactly this rather than
deleted — `week_today` on the date, `week_select_date` on the caret.

### The arrows are sized, and why

`OutlinedButton`'s default minimum width is wide enough that two arrows plus seven
cells stop fitting a phone in portrait, so `WeekArrow` pins the circle to 36.dp with
zero content padding. Material still measures a **48.dp touch target** around it, so
the button is small but the tap is not. That target overhangs the 36.dp circle by 6.dp
per side — which is why the view tree reports the strip starting ~4.dp from the edge
while the painted edge is at 10.dp. Both numbers are correct; do not "fix" the 4.

### Messages are snackbars, and `MessageSnackbar` owns the rule

See §4. The mapping from message to wording stayed per-screen (`messageText`); only the
rendering was centralised. Those mappings use `pluralStringResource`, which is
`@Composable`, so the **text must be resolved in composition and handed to the effect** —
it cannot be looked up inside `LaunchedEffect`.

`onConsume()` runs **after** `showSnackbar` returns, never before. Consuming first
would null the state, which nulls the `LaunchedEffect` key, which cancels the very
snackbar being shown.

## 4. Message banners became snackbars

The complaint that started it: a confirmation "appears like another composable and
scrolls down the current composables". Correct — a `Card` is a layout node. It appeared
*between* the header and the list, pushed everything below it down by its own height,
and needed an OK press to leave. A confirmation that reflows the screen it is
confirming costs more than it tells you.

**New, in `presentation/common/UiComponents.kt`:**

- `LocalSnackbarHostState` — a `staticCompositionLocalOf`. Ambient rather than a
  parameter threaded through five screens: the host lives in the root `Scaffold` and
  every screen inside it wants the same one.
- `MessageSnackbar(text: String?, onConsume: () -> Unit)` — the whole show-and-consume
  rule in one place.

**`App.kt`:** one `SnackbarHostState` for the app, passed to `Scaffold(snackbarHost =)`
so messages land above the navigation bar and two cannot overlap; provided to the
screens through the composition local.

**Each of the five screens:** the `MessageBanner` composable became
`private fun messageText(message: X): String` — same `when`, no `Card`, no `Row`, no OK
button. One call site each:

```kotlin
MessageSnackbar(state.message?.let { messageText(it) }, onConsumeMessage)
```

`BodyWeightScreen` was the odd one: its banner was a `LazyColumn` `item(key = "message")`,
so it had to move **out** of the list, next to `PresetRow`.

Verified on the emulator: `Logged.` renders as a dark snackbar with an X (`Dismiss`)
action at y≈2029, above the nav bar at y≈2277, overlaying content rather than
displacing it.

## 5. Open items

Carried over from 2026-08-21 and still true: **`DISTANCE_TIME` activities cannot be
logged** (`StartOrResumeSessionUseCase` rejects non-`STRENGTH`) — still the biggest
functional gap; iOS is compile-verified only, never run; Monday-first is hardcoded; no
in-app language picker; es/it/fr want a native-speaker pass.

New today:

- **Backslash-quote renders literally in the UI.** Compose Multiplatform's resource
  parser handles `\'` (which is why the apostrophe fix worked) but **does not process
  the `\"` escape**, so the backslash is printed. On screen right now:
  `Use \"New log\" to start one on this day.`
  **6 strings × 4 locales = 24 occurrences**, including `category_delete_title` and both
  `activity_*_for` dialog titles — so every dialog that quotes a name is affected.
  Suggested fix: typographic quotes, not `&quot;` and not a bare `"` (a bare `"` has its
  own whitespace-quoting meaning in Android-style resources, and it is not worth
  depending on how CMP treats it).
- **Double-percent renders literally too**, same root cause. Visible on the Weight
  summary: `Change: -31.0 kg (-25.8%%)`. Should be a single percent sign.
- **Only the Log screen has 10.dp margins.** Activities and Weight are still at 16.dp,
  so their strips are narrower than the Log one when you flip between tabs. This was
  scoped deliberately ("this screen"), not missed.
- **`common_ok` may now be unused** — it was the banners' dismiss button. Not checked.

## 6. How this was verified — worth reusing

Driving the emulator from Git Bash on Windows, the parts that were not obvious:

```bash
ADB="$LOCALAPPDATA/Android/Sdk/platform-tools/adb.exe"
export MSYS_NO_PATHCONV=1   # else Git Bash rewrites /sdcard/ui.xml into a Windows path
```

- **Read the view tree, do not guess coordinates from pixels.**
  `adb shell uiautomator dump /sdcard/ui.xml`, then parse `bounds=` and `text=`. Compose
  semantics show up there, including `content-desc`, which is also how the accessibility
  labels in §3 were confirmed. Guessing tap points off a screenshot produced an
  unreproducible mess early on and cost a full re-test.
- **One interaction per tool call.** Firing `input tap` and `screencap` in one command
  lets the capture outrun the tap; an early "verification" was thrown out for this.
- **`adb shell cat file.png > out.png` corrupts binaries** (line-ending translation).
  Use `adb exec-out screencap -p` or `adb pull`.
- **A 4-second snackbar is hard to screenshot.** Five single captures all missed it.
  What worked: one on-device shell doing
  `input tap …; screencap -p /sdcard/a1.png; screencap -p /sdcard/a2.png`,
  then pulling both — the second frame caught it. A `uiautomator dump` is the reliable
  check; the screenshot is only for the human.
- **`PYTHONIOENCODING=utf-8`** when printing dumped text, or the caret glyph crashes
  cp1252 stdout.

The emulator changed identity mid-session (was `Medium_Phone_API_36.0`, 1080×2400,
Spanish; later 1080×2424 @ 420dpi, English). **Re-read `wm size` and `wm density` before
converting px to dp** rather than reusing a figure from earlier in the session.
