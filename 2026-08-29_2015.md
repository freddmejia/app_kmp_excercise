## 2. Running ships

One entry in `ResourceCategorySeed`, four strings, no migration.

That last part is the seed design paying off: a **new seed key reaches an existing
install on the next launch**, because the ledger — not the schema version — is what
says a key has been applied. `category_seed` had never seen `running`, so the start-up
sync inserted it. Verified on the emulator's real database: four categories, ledger
`bicycle, gym, running, swim`, and the app never migrated.

Three of the four are now `DISTANCE_TIME`, and the file's KDoc had to stop calling that
redundancy: they are different training with separate history — "how far did I run this
month" is unanswerable if a run and a ride land in one bucket.

## 3. The day card lists muscles instead of counting them

Asked for as: *"per item muscles should appear like a pill with his name donde show 2
muscles, delete section effective and warmup."*

Before: `Gym — 3 effective · 1 warmup · 2 muscles`
After: `Gym` with `[Middle chest] [Rhomboids]` under it.

The set counts are gone from the list. Three numbers described a session they did not
name, and the numbers are on the screen you open next anyway. What the list needs to
say about a strength log is **what was worked** — which is also the only thing telling
two Gym logs on one day apart, now that neither carries a name. That is the same
argument that removed activities, applied one level down.

New query `selectDayMuscles`, one per **day** rather than one per row: the list is a
`LazyColumn`, and a per-row query would fire as each card scrolled into view. Grouped
into a `Map<sessionId, List<String>>` in the repository rather than with
`group_concat` — SQLite has no array type, and a concatenated string is one the UI
would have to split, which breaks on the first muscle name containing the separator.

The pills are a `FlowRow`. A session can touch a dozen muscles and a single `Row` would
measure the overflow to zero rather than wrap — the failure mode that once deleted the
New-log button from this very screen (2026-08-25 §6, and again in 2026-08-29 09:40 §4).
They are labels, not controls: a tap does nothing the card does not already do.

The other two shapes keep their own line — a ride still reads `30 km · 50 min · 1:40
/km`, and a log with nothing checked still says so rather than showing an empty row of
pills, which is why the map is *absent* for those rather than empty.

## 4. ⚠️ "I cannot delete it" was not a bug

Reported as one, so it got the full treatment: read the delete path, then reproduce on
the device. `deleteLog` → `DeleteSessionUseCase` → a transaction that removes the
entries and then the session. All correct.

On the emulator the swipe worked, the confirmation appeared, and the row went. It
worked on a **freshly created empty log** too, which is exactly the case reported.

The mechanism was fine. **Deleting was swipe-only** — a gesture with nothing on screen
to suggest it exists. A log created by mistake reads as permanent, and "I cannot delete
it" is the honest description of that.

So the fix is not to the delete path but to the affordance: a **trash button on every
row**, next to the chevron. The swipe still works for anyone who found it; this is the
half that can be found without being told.

Worth keeping: three sessions of tests, all green, said nothing was wrong — because
nothing *was* wrong by the definition the tests hold. Discoverability is not a
behaviour a unit test can assert, and this is the second time in two days the emulator
caught something the suite structurally could not (the other was the missing
`koinViewModel` key).

### And a wrong sentence it turned up
The confirmation dialog for a **ride** read *"Bicycle — 0 effective sets across 0
muscles will be removed."* True, and a description of the wrong thing. It has its own
branch now, naming what the log actually holds: *"Bicycle — 30 km · 50 min will be
removed."*
