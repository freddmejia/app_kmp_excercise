## 3. Two logs of the same kind on one day

Asked directly, and the answer changes the whole identity of a session.

`StartOrResumeSessionUseCase` found a session by (activity, day) and created one only
if it found none. The user chose **create a second log**, so:

- `StartSessionUseCase` **always creates**. Reopening is tapping the row.
- The entry screen is keyed by **session id**, not (activity, day) — the pair no longer
  identifies anything.
- `LogDistanceTimeUseCase` was deleted and replaced by `SetSessionDistanceTimeUseCase`.
  The old one started a session *and* wrote the measures, which was fine while starting
  meant resuming; now it would add a ride to the day every time you corrected a number.
  Starting and measuring are two calls, and correcting writes by session id.

**The screen stopped creating anything.** It used to write the session row on arrival
for a strength log, so "open" and "write" were the same act and a screen opened by
mistake left a row behind invisibly. The row is created by pressing New log and picking
a category — an explicit act — and an abandoned log is a visible row in the day saying
nothing was recorded, which can be deleted from there.

## 4. ⚠️ The migration rebuilds a table, and the order is the whole thing

`workout_session.activity_id` is `NOT NULL REFERENCES activity(id)`, so it had to go
before `activity` could be dropped — and `ALTER TABLE … DROP COLUMN` needs SQLite 3.35
while **minSdk 24 can be as old as 3.9**. That means the classic rebuild, under two
conditions this project cannot control together:

- **Foreign keys may be on.** The iOS driver sets `foreignKeyConstraints = true`. With
  enforcement on, `DROP TABLE` performs an implicit `DELETE FROM` first — so dropping
  `workout_session` while `session_muscle` still referenced it would **cascade and
  silently delete every set ever logged**.
- **`ALTER TABLE … RENAME` differs by version.** Since 3.25 it rewrites references to
  the renamed table in other tables' schemas; before that it does not.

The order that is safe under both: copy the sessions into a new table, park
`session_muscle` in a table with **no foreign key at all**, drop both originals while
nothing references anything, rename, then rebuild `session_muscle` against it.

**The test for this sets `PRAGMA foreign_keys=ON` explicitly.** The JDBC driver has
them off by default, so without that line the suite would pass on a mistake that
destroys the user's history on their phone. That is the single most important line
added this session.

### Where sessions went
A session takes its activity's category. One whose activity had none is matched by
**measurement type** to a category that measures the same thing, preferring a shipped
one (`ORDER BY (seed_key IS NULL), id` — a user's own category cannot win on being
inserted first). If there is no candidate at all, the session keeps its sets and its
day with **no category**, and the UI renders it as "Uncategorised".

Deliberately **no INSERT of a missing "Gym"**: the seed ledger says a shipped row the
user deleted stays deleted, and a migration that quietly put one back to have somewhere
to point would break that rule at the worst possible moment.

Activity *names* are dropped rather than preserved into `notes` — the user's call.

## 5. What a category delete does now

It was the one place the old model was already right: deleting a category is
unrestricted because it is only a label. That survived, and got sharper.

- `workout_session.category_id` is **nullable**, `ON DELETE SET NULL`. Deleting a
  category strips the label off its logs; every set, day and distance survives.
- **Archiving no longer detaches.** It used to move a category's activities to
  uncategorised, because an archived category was a filter you could no longer select
  and its activities would have been stranded in it. What points at a category now is
  *history*, and tidying a picker is not a reason to rewrite the record.
- The management list counts **logs**, not activities: "12 logs" says whether a
  category is in use where "2 activities" only said how much setup had been done.

## 6. The gap the orphaned strings caught

Removing the activity editor orphaned 43 string keys. Working through them surfaced a
real bug: `CategoryEditorViewModel` had gained `measurementType` and
`setMeasurementType` last session, and **its screen never got the control**. Every
category the user created would silently have been a strength one, and the only
categories that could measure distance would have been the two shipped ones.

The measurement chips moved from the activity form to the category form, where they
belong, along with `MeasurementType.labelRes()`. There is a line under them saying the
choice applies to what is logged *next* — changing it does not reach logs already
recorded, and "changes nothing that exists" is not what anyone assumes a type field
does.

Thirty-seven keys removed; three (`log_no_strength_activities`,
`log_distance_time_title`, `plural_days`) were already dead before this session and are
left, still noted.

New:

- **`SIMPLE` is now choosable and still unloggable.** It is one of the three chips on
  the category form, so a user can create a "Yoga" category measured that way — and
  the entry screen has no form for it, falling through to the distance one. It was
  unreachable an hour ago and is now reachable and broken. Either give it a form (a
  name and a day, nothing else) or drop the enum value. **This is the one thing here I
  would fix first.**
- **The muscle picker is no longer scoped.** `activity_muscle` linked an activity to
  the muscles it targets and narrowed the picker; with no activities there is nothing
  to narrow by, and a category is too coarse — "Gym" does not mean chest. The whole
  catalogue is offered, ordered by use. If scrolling 28 leaves gets old, the scope
  belongs on the category.
- **`workout_session.notes` is written by nothing.** It survives in the schema and in
  the day-card model, and it is now the only place a log could carry a word of its own.
  If "chest day" is ever missed, that is where it goes — as a note on one session, not
  as a catalogue.
- **An abandoned log leaves a row.** Pressing New log, picking a category and backing
  out leaves "Gym — nothing checked yet" on the day. Visible and deletable by design,
  but it is a new way to accumulate clutter that did not exist when the form created
  its own row lazily.
- **Three migration tests are pinned to intermediate versions** (`1 → 2`, `1 → 6`) and
  read their tables through raw SQL, because the tables they are about do not exist at
  head. They still guard the steps they describe; they can never again be checked
  against a fresh install.
- **`CategorySelection` and the category filter are gone** with the activity list that
  used them. Nothing filters logs by category yet — the day view shows the day.
