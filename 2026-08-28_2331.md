## 2. The app bar, and why the two platforms did not match

The reported symptom: "for Android and iOS it is not the same". It was not the title —
there was no title. The cause is worth keeping.

`App.kt` padded the whole `Scaffold` with `safeDrawingPadding()`. That keeps content
out of the system bars but leaves the bars' own strips **unpainted by anything Compose
owns**. Android filled them from the window background in `themes.xml`; iOS has no such
thing, so the status bar and the home indicator came out in the system default instead
of the app's surface. Each screen also drew its own headline inside its own padding, so
the title started wherever that screen's content happened to.

Now the Scaffold fills the window and **the two bars pay for the insets they cover** —
`TopAppBar` takes the top, `NavigationBar` already took the bottom, and the body keeps
only the horizontal ones through `contentWindowInsets`. `imePadding()` stays on the
Scaffold, because `safeDrawing` was carrying the keyboard inset too and content still
has to rise above the keyboard; only the *system bar* half moved into the bars.

- The bar's `containerColor` is **named**, not defaulted, to `surfaceContainer` — the
  role the navigation bar already uses. M3's own default here is `surface`, which would
  leave the top of the app flat while the bottom is raised.
- A **back arrow** appears whenever `backStack.size > 1`. New `GymIcons.ArrowLeft`: a
  shaft as well as a head, because `ChevronRight` on its own says "there is more this
  way", and this is the one control that leaves a screen. It is also the *only* way
  back on iOS.
- `ScreenHeader` became **`ScreenActions`** — the title left, the buttons stayed. They
  are deliberately not in the bar's `actions` slot: that slot is a plain `Row`, which
  measures a long translated label to zero rather than wrapping. That is the bug that
  once deleted the New-log button (see 2026-08-25 §6), and the `FlowRow` is what
  prevents it.
- `common_done` had no callers left after the Done buttons went, so the **key was
  renamed** to `common_back` rather than left dead beside a new one.

`TopAppBar` is still experimental in material3 on Kotlin/Native — same shape as
`DatePicker` in `WeekStrip`. The opt-in is annotated with why.

## 3. Navigation: the `Route` enum became a sealed `Screen`

The 2026-08-25 log said: *"Introduce a real nav graph when a route gains an argument."*
Four routes gained one today, and a nav library still is not here — deliberately. What
changed instead:

```kotlin
private sealed interface Screen {
    val destination: Destination
    val title: StringResource
    …
    data class LogEntry(val activityId: Long, val epochDay: Long, val existing: Boolean)
}
```

- **The bar reads the title off the route**, so a screen that knows whether it opened
  onto something existing knows whether to say "New log" or "Edit log". No flicker: the
  alternative is a database read that flips the title a frame after the screen appears.
- `existing` is **passed by the caller**, not derived. The list that was tapped already
  knew — the day's log, the strip's week, the row itself.
- The stack survives process death as a **flat list of `Long`s, four per screen**: a
  tag and three argument slots. Compose Multiplatform has no `Saver` for a sealed type
  any more than for an enum. An unknown tag restores as `WorkoutLog` rather than
  crashing, so a stack written by a future version degrades to the start.
- **Zero is the "does not exist yet" id** everywhere. Safe because every id comes from
  `INTEGER PRIMARY KEY AUTOINCREMENT`, which starts at one.

Ten tags now (`0`–`10`). If a third argument shape appears, or one that is not a
number, that is the moment to reach for a real navigation library rather than widen
this again — the comment in `App.kt` says so.

## 4. The editor pattern — read this before writing the next one

Five screens were built to the same shape. Copy it.

1. **Keyed by what the screen is *about*, not by row id.** The body-weight editor takes
   a *day* (`date_epoch_day` is UNIQUE, and the upsert changes the row's id on every
   correction). The log entry takes *(activity, day)* — `StartOrResumeSessionUseCase`
   finds a session by exactly that pair. Both mean the screen cannot be opened onto a
   row that has meanwhile been deleted: it is simply a create.
2. **`onOpened()` on every visit**, not `init`. A ViewModel resolved by key lives in the
   activity's store and outlives the visit that created it.
3. **`saved` is a `SharedFlow` with no replay**, never a flag in the state.
4. **One `LaunchedEffect(Unit)`, in this order**: `viewModel.onOpened()` then
   `viewModel.saved.collect { onDone() }`. Two separate effects race.
5. **Errors go under the field, not in a snackbar.** A snackbar raised from a
   composition that is being torn down is cancelled with it, and a reason a form was
   refused has to stay readable while the value that caused it is corrected.
6. **Success closes the screen silently.** The list behind it is already showing the new
   value by the time it closes; that is the receipt.

## 5. ⚠️ The bug this pattern exists to prevent

The body-weight editor first held `isSaved: Boolean` in its state. On the emulator,
**tapping a reading did nothing at all** — no error, no crash, no navigation.

The ViewModel is keyed by day and lives in the activity's `ViewModelStore`, so the
instance for that day was still there the second time the day was opened, with
`isSaved` still `true`. `LaunchedEffect(state.isSaved)` read it as its own arrival and
called `onDone()` before a frame was drawn.

Nothing about this is visible in a stack trace. It was found by tapping a row on a
device and watching nothing happen, and it would have shipped otherwise: every test
passed, because a fresh ViewModel per test never carries the flag.

Two halves to the fix, both now in every editor:

- **The signal is a flow with no replay.** An emission with nobody collecting is
  dropped rather than kept, so what reaches the screen is only what happened while it
  was on screen.
- **`onOpened()` reloads from the database**, so the second visit does not open on the
  first one's half-typed number either.

`BodyWeightEntryTest` and `WorkoutEntryTest` each pin the regression by name
(`reopeningADayThatWasSavedDoesNotCloseTheScreenOnArrival`).

## 7. Workout log: one entry screen, two forms

A strength session used to take over the log screen *in place* — same bar, same strip,
a Close button where New log had been. A distance log was a dialog. Both are
`WorkoutEntryScreen` now.

- **The activity's measurement type decides which form appears.** It is recorded
  against the activity already; making the user pick the form before the activity would
  ask them to classify what the app has known since the activity was created.
- **Strength writes as you go** — checking a muscle *is* the write, which is why the
  session row is created on arrival and there is no Save button. **Distance writes

- `WorkoutLogViewModel` lost its session half to `WorkoutEntryViewModel`: the picker

  combine went from nine sources to three.
- `WorkoutMessage` is down to `Deleted` (new — deleting a log used to say nothing at
  all). Everything about *writing* a log is `WorkoutEntryMessage`, on the screen that
  writes it.

## 10. Koin: parameters resolve by **type**, which is a trap

`ParametersHolder.get()` returns the first value assignable to the requested type. Two
`Long`s in a row therefore both come back as the first one — which would have dated
every log entry to its own activity id.

```kotlin
// Wrong: both get() calls return activityId.
viewModel { params -> WorkoutEntryViewModel(params.get(), params.get(), …) }

// Right: destructured, which is positional.
viewModel { (activityId: Long, epochDay: Long) -> WorkoutEntryViewModel(activityId, epochDay, …) }
```

`KoinGraphTest` now asserts the *values* survive the trip, not just that the object
resolves — `assertEquals(20_686L, entry.state.value.epochDay)`, and `isGroup` for the
muscle editor, whose third parameter is a `Boolean` among two `Long`s.

## 13. Verification notes — what cost time

Everything above was checked on `emulator-5554` (1080×2424 @ 420dpi) against the real
database, not just compiled. §10 of the 2026-08-25 log still applies in full. New:

- **A `stateIn(WhileSubscribed)` flow does not run without a collector.** Six tests
  failed at once on `state.value` returning the initial value. A test for such a
  ViewModel has to collect it — `backgroundScope.launch { vm.state.collect {} }` — or it
  is testing a screen nobody is looking at.
- **The Bash tool eats one level of backslash in a heredoc.** `"\\u25BE"` written into a
  Python heredoc arrives as the *character* `▾`, so an anchor containing a Kotlin
  unicode escape never matches. The 2026-08-24 log warns about apostrophes in heredocs;
  this is the same class. Write the script with the Write tool and run it by path —
  which is what every patch after the third one did.
- **Tap the centre of the node, from a fresh dump.** Two "the button does nothing"
  detours turned out to be stale coordinates from a dump taken before the layout
  settled; the third was the real §5 bug. Dump, then tap, every time.
- **`input tap` on a text field can miss the field and hit its floating label.** If the
  text you typed is not in the next dump, that is what happened — aim at the middle of
  the box, not at the label.
