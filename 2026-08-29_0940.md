## 2. A preview for every composable

The ask was literal: *for all composables add preview inside per file, dialogs,
screens, etc.* It was cheap because the work to make it possible had already been done
— every screen is already split into a stateful `XScreen(viewModel = koinViewModel())`
root and a stateless `XContent(state, …)` half. The previews hang off the stateless
half and no screen needed restructuring to get one.

**`presentation/preview/PreviewFixtures.kt` is new.** It holds one coherent dataset —
one user's activities, categories, muscle catalogue, sessions and weight history — and
`PreviewSurface`, the wrapper every preview uses.

- **The fixtures are shared rather than per-file** because the screens render the same
  catalogue from different angles. Built per file, "Bench press" would be muscle 2 in
  one preview and muscle 7 in the next, and previews that disagree about what the data
  *is* stop being a reference for anything.
- **`PreviewSurface` is not decoration.** `LocalSnackbarHostState` throws by design
  when absent, and six `…Content` composables call `MessageSnackbar`. Without the
  ambient provided, those six previews render as a stack trace rather than a screen.
- **The scheme is left to `GymTheme`'s default**, so `@PreviewLightDark` — which works
  by flipping the preview's ui mode, which is what `isSystemInDarkTheme()` reads —
  actually produces two different pictures rather than the same one twice.
- **It lives in `commonMain`, and that is a real cost.** The IDE only scans main source
  sets for `@Preview`; a preview in `commonTest` is invisible to it. Everything is
  `internal` or `private` and unreferenced outside previews, so DCE and R8 can drop it,
  but it is in the source set the shipped binaries are built from. There is no way
  around this that keeps the previews visible to the tooling.

### The annotation is `androidx.compose.ui.tooling.preview.Preview`

Not `org.jetbrains.compose.…`. In CMP 1.11 the multiplatform artifact
(`compose-uiToolingPreview`, already a `commonMain` dependency here) publishes the
annotation under the `androidx` package with the full Android parameter set — `name`,
`group`, `widthDp`, `heightDp`, `locale`, `fontScale`, `showBackground`, `uiMode`,
`device` — and the `PreviewLightDark` / `PreviewFontScale` / `PreviewScreenSizes`
multi-preview annotations alongside it. This was checked by unpacking the sources jar
rather than guessed.

### What got previewed, and what could not

Every composable that renders has one, private helpers included — `DayCell`,
`SetsStepper`, `HistoryRow`, `MuscleScopeBanner`, `CategoryFilterRow`,
`DayPickerDialog`, `NewLogDialog` and the rest.

The `messageText` helpers return a `String` rather than UI, so each got a preview that
renders **every message variant in one column**, in `en` and `es`. That is the only
place the whole set can be read together, which is where a plural that does not agree
shows up. Same treatment for the date formatters in `WeekStrip` — including all three
branches of `weekLabelOf` (same month, across a month, across a year) — and for the
number formatters in `UiComponents`, where the rounding carry (9.97 renders as "10.0",
never "9.10") is the case that reads wrong at a glance in a test.

`Theme.kt` got the one preview that is worth more than the rest put together: **the
whole palette, both schemes, on one sheet**, each swatch painted in its role and
labelled in that role's *on* colour, so an unreadable label is the contrast failure
rather than a description of one.

**`App()` has no preview and cannot have one.** Every branch of its `when` resolves a
ViewModel from Koin down to a SQLDelight driver; a preview would need a database, not a
fixture. Its KDoc now says that at length, and says what covers it instead. Same for
the eleven `XScreen` roots — their `XContent` halves are covered in full.

### What a preview here cannot show

Worth knowing before trusting one:

- **Effects do not run in a static render.** `MessageSnackbar` raises from a
  `LaunchedEffect`, so its preview is an empty scaffold until run in interactive mode.
  Said so in the KDoc rather than leaving it looking broken.
- **Anything behind local state is unreachable.** Every delete confirmation in this app
  is an `AlertDialog` behind a `remember { mutableStateOf(null) }` inside the `Content`
  composable, opened by a swipe. A static preview cannot reach any of them. Each such
  preview says so and says to run it and swipe.
- **They were compiled, not rendered.** Whether Android Studio renders `commonMain`
  previews for this setup, and whether CMP's `stringResource` resolves inside them, was
  not verified — the previews lean on `stringResource` heavily.

## 4. ⚠️ The `Row` that would have eaten the button again

The 2026-08-25 log records a `Row` measuring a translated label to zero and removing
the New-log button from the tree entirely. Dropping a button into `WeekStrip`'s date
row walked straight back into it.

That row is:

```kotlin
Row(horizontalArrangement = SpaceBetween) {
    Row { /* date text + caret */ }   // unweighted, measured FIRST
    trailing()                        // gets whatever survived
}
```

A `Row` measures its unweighted children in order and hands each one everything still
unclaimed. The date is first and as long as the locale makes it, so it is measured
against the **full** width and `trailing` gets the remainder. At a normal font scale on
a 1080px screen there is enough left. At a large font scale there is not — and a `Row`
does not clip a child it cannot fit, it measures it to zero. No pixels, no tap target,
no accessibility node. The button is simply gone, silently, exactly as before.

It fits today, so nothing was visibly wrong and nothing would have been caught by
looking at the emulator.

The fix is one modifier on the date group:

```kotlin
Row(modifier = Modifier.weight(1f, fill = false), …)
```

`fill = false` keeps it at its intrinsic width while there is room, so today's layout is
byte-identical; under pressure it yields and the date wraps instead of the button
vanishing. Weighted children are measured *after* unweighted ones, which puts the
priority the right way round: the control is the thing that must survive, the date is
the thing that can wrap.

`WeekStripSqueezedPreview` pins it at 320dp and at 320dp × 200% font, with "Nouvelle
séance" — the longest of the four locales' labels. **What that preview is for is
checking the button is still there**, which is a thing you can only check by looking.

## 5. Save pinned, form scrolled

Asked for on the same two features' create/edit screens. New shared component:

```kotlin
@Composable
fun FormActionBar(modifier: Modifier = Modifier, content: @Composable ColumnScope.() -> Unit)
```

- **A sibling of the scrolling area, not an overlay.** The scroll viewport ends where
  the bar begins, so nothing is ever hidden underneath and the form needs no
  compensating bottom padding. Content clips cleanly at the bar's top edge, which is
  also what signals there is more above it.
- **`surfaceContainer`**, the same role the app bar and the navigation bar take. This is
  the third bar framing the screen and the three should sit at the same step above it.
- **A slot, not a Save button**, for the same reason `ScreenActions` is one: the label
  and the enablement rule belong to the screen, not to its chrome.
- **The keyboard was already handled** a level up — the root `Scaffold` carries
  `imePadding()`, so the bar rides above the keyboard rather than behind it. Confirmed
  by accident on the body-weight screen, where opening the keyboard moved a bar from
  y=2020 to y=988.

Applied to `ActivityEditorContent` and to `WorkoutEntryContent`'s distance form. The
distance form's button moved *up* out of `DistanceTimeLog` into the screen, because
`DistanceTimeLog` renders inside the screen's 16.dp side margins and a bar with margins
does not read as a bar; `DistanceTimeLog` lost its `onSave` parameter as a result.

**The strength form gets no bar.** Checking a muscle *is* the write and the session row
exists from the moment the screen opens, so there is nothing to save, and a permanently
inert Save under it would be claiming otherwise.

### The comment that was backwards

Both forms carried this, and the body-weight editor still does:

> *Scrollable rather than fixed: a large font scale plus an open keyboard can push the
> button below the fold, and a Save button you cannot reach is the one failure this
> screen cannot afford.*

The premise is right and the conclusion is inverted. Scrolling the button does not keep
it reachable — it guarantees there is a scroll position where it is not. Pinning it is
what makes it always reachable, and costs one bar's height. The comments were replaced
rather than left contradicting the layout.

New notes on driving this emulator from Git Bash:

- **MSYS rewrites device paths.** `adb shell screencap -p /sdcard/x.png` fails with a
  usage dump, because `/sdcard/...` is converted to a Windows path before `adb` sees
  it. Use `adb exec-out screencap -p > file`, and wrap any `adb shell` command
  containing a device path in `MSYS_NO_PATHCONV=1` plus single quotes. This is the same
  family of problem as the heredoc backslash mangling in the 2026-08-28 log.
- **`screencap` can capture the previous frame.** Two screenshots came back
  byte-identical to the one before after a tap that had in fact worked — the UI dump
  proved the tap landed while the PNG showed the old screen. Dump first to confirm
  where you are, then capture.
- **The emulator's input layer can wedge.** After a `KEYCODE_WAKEUP` on a blanked
  screen, no `input tap` or `input swipe` reached the app for several minutes —
  `uiautomator dump` stayed live and correct, `mCurrentFocus` was the app, `pidof`
  returned a pid, logcat had no `FATAL`. It was not a crash and not the app.
  `adb reboot` fixed it; nothing else tried did. Check `input` still works by tapping
  something with a visible effect *before* concluding a screen is broken.
- **A long `input swipe` can navigate.** One swipe intended to scroll a form ended up on
  a different tab with text typed into a field. Swipe short, inside the scroll region,
  and over content with no text fields in it.
